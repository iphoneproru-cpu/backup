# server-backup

Полная резервная копия сервера с панелью **Remnawave**, ботом **Remnashop**, **nginx**, сайтом
и сертификатами. Копия делается каждый день по cron, отправляется на другой сервер по SFTP,
старые копии удаляются (и здесь, и там), об итоге приходит сообщение в Telegram.

Что где лежит, скрипт находит сам по запущенным контейнерам docker compose: пути
прописывать не нужно, один и тот же скрипт работает на серверах с разной раскладкой.

- `backup.sh` — делает копию.
- `restore.sh` — поднимает всё из копии на чистом сервере.

## Что попадает в копию

Перед каждой копией скрипт выводит план по пунктам — тот же текст лежит в архиве
(`SUMMARY.txt`) и коротко приходит в Telegram. Пример с боевого сервера:

```
1) REMNAWAVE — панель
   папка: /opt/remnawave (docker-compose.yml .env)
   база: remnawave-db — PostgreSQL 18, «postgres», 20 MB: пользователей 284, нод 15, хостов 23
   valkey: remnawave-redis — только кэш без тома, сохранять нечего
2) REMNASHOP — бот
   папка: /opt/remnashop (docker-compose.yml .env)
   база: remnashop-db — PostgreSQL 17, «remnashop», 11 MB: пользователей 317, подписок 381, платежей 334
   valkey: remnashop-redis — данные (очереди, кэш), ключей 353; сохраняю dump.rdb
3) NGINX — веб-сервер
   папка: /opt/remnawave/nginx (nginx.conf, сертификаты)
   домены: bot.chebur.xyz my.chebur.xyz panel.chebur.xyz sub.chebur.xyz
4) Страница подписки Remnawave — /opt/remnawave/subscription
5) Остальное в /opt — исходники бота /opt/remnashop-src (ветка, коммит) и прочие папки
6) Сайты — /var/www/my.chebur.xyz
7) Сертификаты — acme.sh / certbot: домены и даты окончания
8) cron, ufw, /root/.ssh
```

Подробно:

| Что | Как сохраняется |
|---|---|
| Базы PostgreSQL во всех контейнерах | `pg_dump -Fc` (без остановки), с версией PostgreSQL |
| valkey / redis с томом `/data` | `SAVE` → `dump.rdb` (кэш без тома пропускается) |
| Именованные тома остальных контейнеров | архив содержимого тома |
| Папки проектов compose | целиком: `docker-compose.yml`, `.env`, конфиги, сертификаты |
| Прочее в `/opt` | исходники с `.git`, скрипты |
| Папки хоста, подключённые в контейнеры | например `/var/www/<сайт>`, `/etc/letsencrypt` |
| Сертификаты | `/root/.acme.sh`, `/etc/letsencrypt` |
| Расписания и доступы | crontab root, свои файлы `/etc/cron.d`, правила ufw, `/root/.ssh` |
| Версии образов | digest каждого образа — при восстановлении берутся те же версии |

**Не попадает:** логи, папки `backup`/`backups` внутри `/opt` (старые дампы и архивы других
скриптов), файлы данных баз (вместо них дампы), `/opt/containerd`, сами архивы копий.

## Установка

На сервере, который нужно бэкапить (под root):

```bash
git clone git@github.com:iphoneproru-cpu/backup.git /opt/server-backup
bash /opt/server-backup/backup.sh
```

Откроется меню (цветное, вверху — расписание, сервер копий, Telegram и последняя копия).
Пункт 4 «Показать, что попадёт в копию» ничего не делает — только показывает. Проверьте, что все
проекты и базы на месте.

Если репозиторий закрытый, серверу нужен ключ для чтения: `ssh-keygen -t ed25519 -f
~/.ssh/backup_repo -N ""`, публичную часть добавить в GitHub → репозиторий → Settings →
Deploy keys (без права записи), и клонировать так:
`GIT_SSH_COMMAND="ssh -i ~/.ssh/backup_repo" git clone git@github.com:iphoneproru-cpu/backup.git /opt/server-backup`.

## Настройка

Меню → пункт 5 «Настроить». Скрипт задаёт вопросы; в квадратных скобках — значение по умолчанию (Enter — оставить).

1. **Время копии** — по московскому времени; в cron записывается по часам сервера.
2. **Папка для копий на этом сервере** (по умолчанию `/root/backups`) и сколько копий там хранить (по умолчанию 7).
3. **Сервер для копий** — IP или домен, порт SSH, затем:
   - **логин** пользователя на том сервере (по умолчанию `backup`; скрипт создаст его сам) —
     под этим именем боевой сервер будет заходить туда и класть копии;
   - **подпапка** в домашней папке этого пользователя (по умолчанию — имя боевого сервера,
     например `iphoneproru`), чтобы копии разных серверов не смешивались.

   Итог при значениях по умолчанию: копии лежат в `/home/backup/iphoneproru` на сервере
   для копий (у системного пользователя `backup` в Ubuntu домашняя папка — `/var/backups`, тогда
   `/var/backups/iphoneproru`). Точный путь скрипт показывает после проверки доступа (меню → пункт 8).

   Ещё спросит, сколько копий хранить там (по умолчанию 30).
   Пусто — копии остаются только на этом сервере.
   - **Ключ SSH:** отдельный ключ `/root/.ssh/server_backup_ed25519` (создаётся сам) или свой.
   - **Доступ на том сервере** — на выбор:
     - *автоматически*: скрипт один раз зайдёт туда под root (спросит пароль) и создаст
       пользователя без командной строки, папку для копий и добавит ключ;
     - *вручную*: скрипт покажет команды, которые нужно выполнить там под root.

     Ключ добавляется с ограничением `restrict,command="internal-sftp"`: этим ключом можно
     только загружать и удалять файлы по SFTP — ни командной строки, ни доступа к чему-то
     ещё. Если этот сервер взломают, с копиями на другом сервере ничего больше сделать нельзя.
4. **Telegram:**
   - от бота магазина владельцу (берёт `BOT_TOKEN` и `BOT_OWNER_ID` из `/opt/remnashop/.env`);
   - от другого бота — токен и chat id (свой id подскажет @userinfobot, у группы id с минусом);
   - не присылать.

   И когда писать: после каждой копии или только при ошибке. В конце уходит проверочное
   сообщение.

Ответы сохраняются в `/opt/server-backup/backup.conf` (права 600, в git не попадает),
в crontab добавляется строка с пометкой `# server-backup`. Повторная настройка меняет
настройки и строку cron, ничего не дублируя. В конце скрипт предложит сразу сделать первую копию.

## Использование

`bash /opt/server-backup/backup.sh` — меню:

| Пункт | Что делает |
|---|---|
| 1 | Сделать копию сейчас |
| 2 | Сделать копию без отправки на сервер копий |
| 3 | Разовая копия: только выбранные проекты или без каких-то, дополнительные файлы и папки, с отправкой или без (backup.conf не меняется) |
| 4 | Показать, что попадёт в копию (ничего не копирует) |
| 5 | Настроить: время, хранение, сервер копий, Telegram |
| 6 / 7 | Поставить расписание из настроек / снять его |
| 8 | Проверить доступ к серверу копий |
| 9 | Команды для настройки сервера копий |
| 10 | Отправить проверочное сообщение в Telegram |

Без терминала (cron) тот же запуск сразу делает копию — меню не появляется.

Постоянно пропускать проекты или добавлять папки — в `backup.conf`:
`SKIP_PROJECTS="a b"`, `EXTRA_PATHS="/root/notes /etc/something"`.

### Только один проект

Разово — меню → пункт 3, постоянно — `ONLY_PROJECTS="remnadiag"` в `backup.conf`: в копию идут только контейнеры
этого проекта (его папка, дампы баз, тома) и `EXTRA_PATHS`. Остальное на сервере — другие проекты, `/opt`, сайты,
сертификаты, cron, ufw, `/root/.ssh` — не копируется. Так делает копии дашборд RemnaDiag.

### Служебные ключи (для cron и агента RemnaDiag)

Человеку они не нужны — всё есть в меню. Агент RemnaDiag вызывает:

```bash
bash /opt/server-backup/backup.sh --apply-cron     # поставить расписание из backup.conf (CRON_TIME, часы сервера)
bash /opt/server-backup/backup.sh --remove-cron    # снять расписание
bash /opt/server-backup/backup.sh --check-remote   # есть ли доступ к серверу копий (код 0 — есть)
bash /opt/server-backup/backup.sh --remote-cmds    # команды для того сервера (создаст ключ, если его нет)
```

`STATUS_FILE=/путь` в `backup.conf` — после каждой копии там итог по строке `key=value`: `status` (`running`,
`ok`, `failed`), `at`, `archive`, `size`, `uploaded`, `failed_at`, `error`, `warnings`.

- Лог всех запусков: `/var/log/server-backup.log` (сам обрезается после 5 МБ).
- Два запуска одновременно не пойдут — второй сразу завершится.
- Если свободно меньше 500 МБ, копия не делается (и приходит сообщение об ошибке).

• NGINX — веб-сервер

При ошибке — ❌, шаг, на котором остановилось, и последние строки лога. Если сертификат
истекает меньше чем через 14 дней, это попадёт в предупреждения.

## Архив

`/root/backups/server-backup-<сервер>-<ГГГГММДД-ччммсс>.tgz` (время UTC), внутри:

```
SUMMARY.txt        что в копии (тот же план, что на экране)
MANIFEST           когда, с какого сервера, IP, коммит бота
containers.txt     контейнеры, проекты compose, образы с digest
db/*.dump          дампы PostgreSQL + db/list.txt
redis/*.rdb        данные valkey
volumes/*.tgz      именованные тома
files.tgz          файлы (/opt, /var/www, сертификаты, /root/.ssh, …)
crontab.txt, ufw.txt
backup.sh, restore.sh
```

Посмотреть копию, ничего не восстанавливая:

```bash
tar -xzf server-backup-….tgz -O --wildcards '*/SUMMARY.txt'
```

## Восстановление на новом сервере

1. Чистый Ubuntu/Debian, root. Скопируйте туда архив (с сервера копий: `sftp`/`scp`).
2. Достаньте `restore.sh` из архива и проверьте:

   ```bash
   tar -xzf server-backup-….tgz --wildcards '*/restore.sh' --strip-components=1
   bash restore.sh server-backup-….tgz --check
   ```

3. Восстановите:

   ```bash
   bash restore.sh server-backup-….tgz
   ```

   Порядок: файлы → docker (если нет — предложит поставить) → образы тех же версий →
   контейнеры → данные valkey и тома → базы из дампов → запуск → cron → проверка доменов.
   На сервере, где уже есть такие контейнеры, скрипт остановится (`--force` — если уверены);
   базы с данными не перезаписываются никогда.
4. Если IP сменился — поменяйте A-записи доменов (Cloudflare). Ноды Remnawave подключатся
   к панели сами, когда DNS обновится. Правила ufw старого сервера — в `ufw.txt` архива.

## Удаление

```bash
crontab -l | grep -v '# server-backup' | crontab -
rm -rf /opt/server-backup /root/backups /var/log/server-backup.log
```
